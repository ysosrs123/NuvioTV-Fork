## Findings

1. **P1 — reversing a backward preview can seek beyond live.** In `resolveLivePreviewSeek`, `pendingPreviewPosition` contributes only to backward deltas; a forward delta uses the actual player position. With player=50 s, buffer=53 s, raw delay=0, a -30 s preview selects 20 s. A subsequent +10 s command with displayed delay=30 s selects **60 s**, with `snapToLive=false`, instead of 30 s. This exceeds even the supplied buffered position. The caller keeps the real player at its existing position until commit, so the discrepancy is reachable through `OnPreviewSeekBy`. Preserve the preview anchor for both directions, and clamp to an actual seekable window. [Policy lines 180–200](https://github.com/halibiram/NuvioTV/blob/e10c639200d5821d1cbc71bdd438ccbd6b1ff7ff/app/src/main/java/com/nuvio/tv/ui/screens/player/LivePlaybackUiPolicy.kt#L180), [preview caller](https://github.com/halibiram/NuvioTV/blob/e10c639200d5821d1cbc71bdd438ccbd6b1ff7ff/app/src/main/java/com/nuvio/tv/ui/screens/player/PlayerRuntimeControllerPlaybackEvents.kt#L1313).

2. **P2 — the LIVE latch can conceal a measured delay indefinitely.** A new filter, current=10 s, buffer=13 s, measured live offset=20 s produces raw delay=17 s, but its playing update reports **0 s / LIVE**. The playing branch retains zero whenever locked and does not reconcile against the measured offset; the controller supplies play intent through rebuffering. This smooths the label by hiding real delay. A display filter should converge to reliable timeline measurements, with an explicit unknown state when timing is unavailable. [Filter playing branch](https://github.com/halibiram/NuvioTV/blob/e10c639200d5821d1cbc71bdd438ccbd6b1ff7ff/app/src/main/java/com/nuvio/tv/ui/screens/player/LivePlaybackUiPolicy.kt#L388), [controller inputs](https://github.com/halibiram/NuvioTV/blob/e10c639200d5821d1cbc71bdd438ccbd6b1ff7ff/app/src/main/java/com/nuvio/tv/ui/screens/player/PlayerRuntimeController.kt#L395).

3. **Retention/recovery design concern for our implementation.** `shouldRejoinLiveEdge(90000,45000,1000)` returns true using the configured forward-load buffer target as the retainable window. It has no input for the manifest DVR window, actually retained sample bounds or local capture retention. A stream 90 s behind can still be playable inside a much longer server DVR window; brief low buffer is not proof that content was evicted. The controller then seeks to default position or reloads MPV. Recovery must use actual bounds/behind-window evidence and our governed acquisition lifecycle, particularly while recording or retaining a pause anchor. [Recovery predicate](https://github.com/halibiram/NuvioTV/blob/e10c639200d5821d1cbc71bdd438ccbd6b1ff7ff/app/src/main/java/com/nuvio/tv/ui/screens/player/LivePlaybackUiPolicy.kt#L241), [recovery actions](https://github.com/halibiram/NuvioTV/blob/e10c639200d5821d1cbc71bdd438ccbd6b1ff7ff/app/src/main/java/com/nuvio/tv/ui/screens/player/PlayerRuntimeControllerErrorRecovery.kt#L330).

## Relevance to the IPTV branch

Useful requirements: live-specific controls, stable focus/scrubbing, explicit return-to-live, handling behind-live-window errors, and separating presentation smoothing from raw measurements. Preserve those requirements in our own Nuvio UI.

Do not import this PR wholesale. It modifies the upstream unified runtime, while the current IPTV adapter has purpose-aware admission and request closure. It is not a recording/timeshift capture implementation. Our HUD reports manifest live offset as a measurement or unavailable, and must not infer real retention from a RAM buffer setting. Add direction-reversal, late join, stall, manifest-window movement, long-pause retention and concurrent recording cases to forthcoming timeshift validation.
